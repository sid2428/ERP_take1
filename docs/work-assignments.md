## 1. Shared rules (every team)

### 1.1 Way of working
1. Set up the project with **[SETUP.md](../SETUP.md)** (Option A to start on pages quickly, Option B for database work).
2. One branch per task: `git switch -c exm-2.1-marks-entry` (prefix = your team code, then the task number).
3. Open a **pull request into `main`**. T0 reviews and merges, then applies migrations to Supabase and deploys.
4. Before every PR: `npm run typecheck` and `npm test` pass, and the new pages work on desktop **and** phone width.
5. **Never commit secrets** (passwords, connection strings) or the raw CSVs. Credentials are shared privately (`CREDENTIALS.md`).

### 1.2 Database rules
- Everything lives in the `erp` schema. Use the existing style: `snake_case`, `GENERATED BY DEFAULT AS IDENTITY` keys, `CHECK` constraints, enums via `CREATE TYPE`, and `SET search_path = erp, public;` at the top of each migration.
- **Never edit an applied migration.** Always add a new file, numbered **inside your team's range** so files from different teams never collide:

  | Team | Range | Team | Range |
  |---|---|---|---|
  | T0 platform | `009`–`019` | T5 examination | `050`–`059` |
  | T1 student | `020`–`029` | T6 fees | `060`–`069` |
  | T2 faculty & HR | `030`–`039` | T7 placement | `070`–`079` |
  | T3 academic | `040`–`044` | T8 communication | `080`–`089` |
  | T4 attendance | `045`–`049` | | |
- The migration runner applies every file it has not applied yet, so teams can merge in any order. If your migration depends on another team's table, say so in a comment at the top and wait for theirs to be merged.
- **The DBMS evaluation matters:** every team must deliver at least **2 views, 1 trigger, 1 function or procedure, and CHECK/foreign-key constraints** that enforce its business rules *in the database* (not only in TypeScript).
- Every write made through the portal runs in a **transaction** and adds an `audit_log` row (`src/lib/audit.ts`).
- The app role `erp_app` has a **15 s statement timeout**. Avoid per-row correlated subqueries over views on big tables; aggregate once with a CTE (see `/admin/sections` in `src/routes/admin/academic-routes.ts`).
- **Size budget:** the free database holds 500 MB and about 111 MB is used. Stay within your budget (`npm run db:verify` prints sizes):
  T5 ≤ 90 MB · T6 ≤ 30 MB · T4 ≤ 20 MB · T2 ≤ 15 MB · T7 ≤ 15 MB · T8 ≤ 10 MB · T1/T3 ≤ 10 MB each · reserve ~200 MB.

### 1.3 Code and UI rules
- Routes go in `src/routes/<area>-routes.ts`, SQL in `src/queries/<module>-queries.ts`, and pages in `views/<role>/<module>-*.ejs`. Use kebab-case file names.
- Use parameterised SQL only (`$1`, `$2`, …). Validate every form with `zod`. Check permissions on the server for **every** route, never only by hiding links.
- Use the design system in `public/css/app.css` (cards, hero, pills, bars, tables, forms) and the partials in `views/partials/`. No new CSS frameworks, light theme only, and it must work at 390 px phone width.
- Add your pages to the sidebar in `src/lib/nav.ts` only when they work (no dead links).
- Seed data for your module: add `scripts/data/<module>.py`, called from `build_dataset.py`, and list every generated table in the cleanup report.
- Tests: `tests/db/<module>.test.ts` for database rules (run inside rolled-back transactions; see `tests/db/helpers.ts`) and `tests/app/<module>.test.ts` for pages and permissions.

### 1.4 What every team hands in
1. Migrations, code, seed data and tests (merged into `main`).
2. `docs/modules/<module>.md`: the tables (with keys), the rules and where each is enforced, and the views, triggers and procedures with one example query each. This goes straight into the final report.
3. A 3-minute demo script: which account to sign in with and what to click.

## T5 · Examination
**Decided rules (labelled "demo grading rules" in the portal):**
- Every course is marked **in-sem 20 + internal 20 + end-sem 60 = 100**.
- Pass = **total ≥ 40 and end-sem ≥ 24/60**.
- Grades:

| Total | 90–100 | 80–89 | 70–79 | 60–69 | 50–59 | 45–49 | 40–44 | < 40 or end-sem < 24 | absent in end-sem |
|---|---|---|---|---|---|---|---|---|---|
| Grade | O | A+ | A | B+ | B | C | P | F | AB |
| Points | 10 | 9 | 8 | 7 | 6 | 5 | 4 | 0 | 0 |

- **SGPA** = Σ(credits × points) ÷ registered credits of that semester.
- **CGPA** is the same over all semesters; an F counts 0 until cleared, and the passing attempt replaces it.
- An F or AB is a **back subject**, cleared by a supplementary end-sem. In-sem and internal marks carry over, and the attempt number is stored.

| 1.2 | Function `grade_for(total, end_sem, absent)`; procedure `publish_results(course_id, session_id)` computing grades, SGPA and CGPA; trigger blocking mark edits once Locked; contract **`v_student_academic_standing`**. |

## 4. Definition of done (every task)
