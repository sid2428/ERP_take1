# Group 3 schema reconciliation

This migration adapts the MySQL/MariaDB Group 3 attendance and examination references to the portal's PostgreSQL schema. It adds the examination objects only; the portal already has the Group 3 attendance model and its tables must not be duplicated.

## Dialect and loading differences

- The reference SQL targets MySQL 8/MariaDB (`CREATE DATABASE`, `USE`, `AUTO_INCREMENT`, `ENUM`, `TINYINT`, `DATETIME`, inline `INDEX`, `IF`, `SIGNAL`, `DELIMITER`, and `LOAD DATA LOCAL INFILE`). The portal runs PostgreSQL in schema `erp`; the migration uses `SET search_path`, PostgreSQL enum types, identity columns, `boolean`, `timestamptz`, indexes, PL/pgSQL triggers, and `RAISE EXCEPTION`.
- `load_data.sql` and `load_exam_data.sql` are MySQL bulk loaders. They were not run and are not portable to PostgreSQL. No data was loaded by this reconciliation.
- Migrations use sequential names; `084-group3-examination.sql` follows the existing `083` migration.
- The exam schema is created empty. `grade_scale` intentionally has no seed rows: grade-band policy needs approved source data before loading.

## Attendance and shared-table reuse

| Group 3 reference | Portal implementation / adaptation |
|---|---|
| `division` | Already exists as `erp.division`; uses `dept_id` and `academic_session_id` FKs rather than source `department_id` and `academic_year`. |
| `batch` | Already exists as `erp.batch`, with `batch_no` and division consistency constraints. |
| `student_section_mapping` | Replaced by `erp.student_section`, keyed by integer `student_id` and `academic_session_id`; `roll_no` is the portal's column name. |
| `course_attendance_config` | Not created. Course metadata, type and attendance threshold are in `erp.course` (`course_type` values `TH`, `LAB`, `TUT`; threshold `min_attendance_pct`). |
| `teaching_assignment` | Already exists and uses `academic_session_id`, `division_id` or `offering_id`, integer `faculty_id`, and `session_kind`. |
| `attendance_session` | Already exists with `session_status`, absentee ID array, and portal faculty/student IDs. |
| `attendance_record` | Not created as a stored table. `erp.v_attendance_record` expands each conducted session and assignment roster to per-student `P`/`A` rows. |
| `attendance_summary` | Already exists keyed by `student_id`, `course_id`, and `academic_session_id`; totals refresh from attendance sessions. It exposes `attendance_pct` through `v_student_attendance_by_course`. |
| Attendance views | Portal views already exist, with `student_id`, `academic_session_id`, `course_code`, and portal naming. The original MySQL views are not recreated. |

The current local database is PostgreSQL 17 and already contains the portal schema (52 ERP tables before this migration). Therefore there is no second attendance migration or duplicate attendance data model.

## Examination table adaptations

- The migration reuses the existing `course`, `student`, `faculty`, and `academic_session` tables rather than introducing Group 3 copies.
- `course_exam_scheme.course_id`, schedules, marks, and results reference `course.course_id`; `course_name`, `course_type`, `credits`, and `min_attendance_pct` remain owned by `course`. The redundant `credits` column was removed from the exam scheme/results and is read from `course`.
- Student-facing exam tables store and foreign-key the portal's integer `student_id`. Views join `student` to expose the external `student_number` where useful. The reference string `student_number` is an institutional login/identifier, not the portal's relational key.
- Mark-entry ownership uses the portal's integer `faculty_id` FK to `faculty`, not faculty codes or login IDs. `entered_by` references faculty. The sample Group 6 CSV uses `Employee_Code` values like `F2005001`; the portal's synthetic faculty `faculty_code` uses values like `FAC-CSE-014`. Do not substitute either code for `faculty_id`.
- The source `department_id` maps to portal `dept_id` (`varchar(10)`) on department/faculty data. `course` also identifies its home department with `dept_id`.
- `exam_cycle` references `academic_session.session_id` instead of copying `academic_year` plus `semester_type`; the existing `academic_session` carries `academic_year` and `term_type` (`ODD`/`EVEN`). Session identity supplies term context for attendance and assignments.
- Result tables retain the program semester number for student transcripts, but key semester summaries by `(student_id, academic_session_id)`, avoiding the source unique key that would collide when the same student reaches the same semester in another year.
- `is_final_attempt` is PostgreSQL `boolean`, not MySQL `TINYINT(1)`. Source ENUMs are PostgreSQL enum types in this migration. Numeric counts use `smallint` where appropriate; generated keys use `GENERATED BY DEFAULT AS IDENTITY` so future imports may preserve source IDs.
- `calculate_cgpa` now accepts integer `student_id` and reads course credits from `course`. The registration trigger reads attendance from `v_student_attendance_by_course`, derives the term through the cycle's `academic_session_id`, snapshots the percentage, and blocks a `Registered` row if attendance is missing or below `course.min_attendance_pct`.
- The source hall-ticket, timetable, result-sheet, and faculty mark-entry views are adapted to portal keys and tables. Faculty assignment/roster visibility uses `teaching_assignment` and `v_assignment_roster`.

Per-table examination mapping:

| Source table | Reconciled table and notable changes |
|---|---|
| `grade_scale` | Same purpose; PostgreSQL numeric bounds and `smallint` grade points. Empty until grade policy/data is approved. |
| `course_exam_scheme` | Same table name; references `course`; removes copied `credits`; enforces `total_max` equals the three component maxima. |
| `exam_cycle` | Same table name; generated-by-default integer key; replaces `academic_year`/`semester_type` with `academic_session_id`; keeps exam type, dates, registration window, and status. |
| `exam_schedule` | Same table name; references portal `course` and `exam_cycle`; source enums become PostgreSQL enum types. |
| `exam_registration` | Same table name; `student_number` becomes FK `student_id`; percentage remains as a registration-time attendance snapshot, populated by the trigger. |
| `hall_ticket` | Same table name; `student_number` becomes FK `student_id`; retains cycle uniqueness and ticket/count/status fields. |
| `exam_marks` | Same table name; student and faculty references use integer portal IDs; retains attempt and nullable mark components. |
| `course_result` | Same table name; uses `student_id` and `academic_session_id` instead of student number and academic year; keeps semester and attempt; course credits are looked up instead of copied. |
| `semester_result` | Same table name; uses `student_id` and `academic_session_id`; uniqueness is per student per academic session, not per student per semester-ever. |
| `student_cgpa` | Same table name; student number primary key becomes `student_id` FK; retains the cached CGPA/credit/backlog fields. |

## Identifiers, columns, and dates

- Portal tables and columns use lowercase `snake_case`, generally singular table names. The source files use several names that differ: `roll_no` is retained in the portal as `roll_no` (not `roll_number`); source `student_number` is not renamed to `student_id` in presentation, but foreign keys use `student_id`.
- PostgreSQL `date` columns store date values, not formatted strings. Source fields supplied as `DD-MM-YYYY` must be explicitly parsed during a future importer (for example with PostgreSQL `to_date(value, 'DD-MM-YYYY')`); they must not be inserted as unvalidated text or depend on server `DateStyle`. The sampled `faculty_faculty.csv` `Joining_Date` values are ISO `YYYY-MM-DD`, so source date formatting is not uniform.
- MySQL `DATETIME`/`DATE` values are mapped to PostgreSQL `timestamptz` for event timestamps (`registered_on`, `last_updated`) and `date` for calendar dates. The portal database timezone is Asia/Kolkata.
- In `student_section_mapping`, department/year/semester/academic-year values are not copied into a parallel mapping table: department and year/semester are available through `division`; academic-year/term is available through `academic_session`; the student's `roll_no` remains on `student_section`.

## Deliberate scope and gaps

- The migration creates the exam tables, attendance-based registration guard, CGPA function, and exam views. It does not load attendance or examination data, add routes/API, or change the frontend.
- Attendance corrections, session marking routes, examination workflows/pages, grade-scale seed policy, and a PostgreSQL replacement data importer remain separate implementation work.
